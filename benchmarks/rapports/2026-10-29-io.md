# Entrées-sorties Linux : analyse exploratoire du 29 octobre 2026

Cette analyse concerne `file_io` et `source_scan` du banc Terra. Elle ne démontre pas un
gain après correction. Une première tentative `strace -c` sur les exécutables des trois
langages a échoué avec `PTRACE_TRACEME: Operation not permitted`. Un profil `perf`
en mode utilisateur a ensuite été réalisé sur `source_scan` ; il ne mesure pas les
syscalls ni le temps noyau.

## Observation dans le code et l'IR

Sur Linux, `std.io.read_bytes` appelle `std.sys.read_file`, qui réserve 65 536 octets
avant **chaque** appel à `read`, y compris celui qui constate la fin de fichier
([linux.nx](../../lib/std/sys/linux.nx), `read_file`). Le vecteur démarre vide et
`Vec.reserve` demande une capacité géométrique ([vec.nx](../../lib/std/vec.nx)).

Avec un premier `read` non vide de moins de 65 536 octets, le second appel à `reserve`
demande au moins 65 537 octets et fait passer la capacité du vecteur de 65 536 à 131 072.
Pour ces tailles, l'allocateur Linux de ce commit ajoute un en-tête de 16 octets puis
arrondit la taille mappée à un multiple de 65 536 : première allocation de 131 072
octets mappés, puis nouvelle allocation de 196 608 octets. `heap.realloc` copie l'ancienne
taille **utilisable**, soit 131 056 octets, puis libère l'ancien mapping
([heap.nx](../../lib/std/heap.nx)). Même séquence après une lecture initiale de 65 536
octets. Il s'agit d'une déduction pour les chemins de succès concernés, pas d'un comptage
des appels effectivement observés par traceur.

L'IR optimisée produite par la commande suivante garde deux appels à
`std.vec.Vec.reserve[u8]` avec `65536` : avant le premier `read` puis sur le retour de
boucle. `std.heap.realloc` conserve un `llvm.memmove` de la taille utilisable précédente.
Les noms internes et numéros d'instructions peuvent varier selon le compilateur :

```sh
nxc build benchmarks/terra/source_scan.nx --emit llvm-ir --release -o /tmp/source_scan.ll
rg 'reserve\[u8\].*65536|llvm.memmove' /tmp/source_scan.ll
```

## Échantillons CPU en mode utilisateur

`perf` 6.12.111, événement logiciel `cpu-clock:u` à 997 Hz, a suivi 100 processus
`source_scan` NEXUL, soit environ 40 000 lectures du vrai fichier `lib/std/io.nx`
(3 783 octets, SHA-256 `65243c1cdaad63730162803054dfda1c8dc517b98543013befa0dd7ac2cf52a0`).
La mesure a été lancée depuis la racine du worktree, avec l'exécutable release statique
sans symboles `source_scan` (SHA-256
`bf58a81547f6d770607d88a7b22cab09cc2d0dab40de24c2b2b16705e623d9df`). Il a été construit
avec le `nxc` mentionné ci-dessous et les sources du banc identiques au commit `9033536`.
Le rapport `perf` contient **655 échantillons, aucun perdu** ; sa
[sortie complète](2026-10-29-io-perf.txt) est conservée. Les pourcentages sont pondérés
par période et rapportés à l'ensemble des échantillons, y compris un peu de temps du
shell ; ils ne représentent pas une part du temps mural ni du temps noyau.

| Instructions du binaire mesuré | Part approximative des échantillons | Observation |
|---|---:|---|
| `0x204d50`–`0x204d69` | 63,67 % | Boucle de copie vectorielle (`movups`, deux blocs de 16 octets par tour). |
| `0x2040a0`–`0x2040f4` | 33,28 % | Boucle de classification ASCII et d'accumulation. |

Ces plages proviennent de `objdump -d` ; les offsets affichés par `perf` sont
respectivement `0x3d50`–`0x3d69` et `0x30a0`–`0x30f4` (mapping ELF propre à ce
binaire). L'échantillonnage pointe une copie coûteuse, cohérente avec la réallocation
repérée dans l'IR. Le binaire étant dépouillé de symboles et l'enregistrement ne
contenant pas de pile d'appels, il ne prouve pas quelle fonction appelle cette copie.
Ces résultats ne sont pas extrapolables à `file_io` ni au temps d'attente système.

Reproduction, depuis la racine avec `nxc`, `perf` et `objdump` disponibles :

```sh
nxc build benchmarks/terra/source_scan.nx --release -o /tmp/nexul-source-scan
perf record -e cpu-clock:u -F 997 -o /tmp/nexul-source-scan.data -- sh -c '
  i=0; while [ "$i" -lt 100 ]; do /tmp/nexul-source-scan >/dev/null || exit 1; i=$((i+1)); done
'
perf report --stdio --no-children --percent-limit 0 -i /tmp/nexul-source-scan.data
objdump -d /tmp/nexul-source-scan
```

Les adresses, échantillons et proportions sont propres à cette compilation et à cette
machine ; une reproduction peut en donner d'autres. Le fichier brut `perf.data` de cet
essai n'est pas inclus dans le dépôt.

## Test de sensibilité à la taille

Le script [profile_io.py](../terra/profile_io.py) compile les mêmes programmes
`source_scan` en C, Rust et NEXUL. Il exécute chaque binaire sans argument dans un
répertoire temporaire isolé contenant `lib/std/io.nx` de taille contrôlée, rempli avec
le seul octet ASCII `a`. Chaque processus lit ce fichier 400 fois. Le script effectue
sept passages par langage et taille, alterne l'ordre des langages, vérifie l'identité
des sorties et conserve les sept temps, les empreintes et les commandes dans le
[JSON](2026-10-29-io.json). Les temps muraux incluent démarrage, lecture, balayage et
sortie ; les fichiers sont chauds dans le cache du système.

```sh
cargo build --release -p nxc
python3 benchmarks/terra/profile_io.py --nxc target/release/nxc --output /tmp/nexul-io-probe.json
```

Le fichier de résultat doit être nouveau. Mesure du 29 octobre, Linux x86-64, AMD EPYC
9V74, GCC 14.2, Rust 1.99.1, nxc 0.3.0, LLVM 19 ; machine partagée et arbre de travail
modifié. Le binaire `nxc` est celui construit depuis la base `7f3ddff` ; aucune
différence de `compiler/` ou `lib/` entre cette base et le commit relevé `0ca733e`.

| Taille du fichier | C (ms) | Rust (ms) | NEXUL (ms) |
|---|---:|---:|---:|
| 0 octet | 1,239 | 1,419 | 1,409 |
| 1 octet | 1,276 | 1,315 | 18,018 |
| 3 783 octets | 2,940 | 2,374 | 19,255 |
| 65 536 octets | 28,130 | 22,314 | 58,943 |

Le saut de 0 à 1 octet est cohérent avec le passage dans la boucle de réallocation
décrit ci-dessus ; il ne prouve pas à lui seul que cette opération explique tout l'écart.
Les programmes utilisent les API de fichiers propres à chaque langage : le résultat ne
se limite donc pas au coût du système de fichiers. Le balayage compte des mots ASCII et
n'est pas le lexer complet ; les fichiers synthétiques ne sont pas du code NEXUL valide.

## Suite à demander à Main

La lecture de fichier de `lib/std/sys/linux.nx` est hors du mandat réseau de Terra.
Demander à Main d'examiner la stratégie de réservation et de décider qui corrige. Une
solution doit préserver les lectures partielles, pipes, fichiers changeants, `EINTR`,
EOF et erreurs ; vérifier les fuites et les autres plateformes. Mesurer avant/après avec
les mêmes binaires et protocole, puis vérifier les tests existants. Les gains et leur
causalité restent à établir.
